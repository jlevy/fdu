# fdu Live Uncached Tool Comparison, 0.1.0 Release Candidate

**Date:** 2026-09-16

**Status:** Local performance evidence, measured on the 0.1.0 release candidate

## Outcome

On a reproducible 1,000,001-entry tree, a fresh fdu process with its persisted cache
disabled built a reusable exact index and rendered a depth-one, ten-row tree in a
**5.206-second median**, faster than every other tool measured.
The nearest, `dumac`, took 11.3% longer while returning one number.

| Tool | Work class | Median wall | Versus paired fdu | 95% interval | Peak RSS |
| --- | --- | ---: | ---: | ---: | ---: |
| **fdu** | reusable exact index and 10-row tree | **5.206 s** | baseline | — | 285.4 MiB |
| dumac | allocated-byte total only | 5.637 s | +11.3% | +5.8% to +13.5% | 29.4 MiB |
| diskus | scalar total only | 6.972 s | +34.7% | +29.5% to +41.2% | 10.7 MiB |
| dust | allocated-byte total only | 8.292 s | +60.6% | +58.6% to +68.5% | 640.7 MiB |
| dua | scalar total only | 8.744 s | +63.1% | +61.8% to +79.3% | 21.2 MiB |
| bsd-du | system serial traversal, one total | 51.226 s | +898.0% | +888.3% to +952.3% | 1.2 MiB |
| gnu-du | GNU serial traversal, one total | 65.775 s | +1177.2% | +1154.6% to +1192.5% | 5.8 MiB |

Every competitor here returns one number.
fdu returned file and directory counts, apparent and allocated bytes, newest file time,
per-directory roll-ups for the whole tree, and per-extension tallies, and kept the index
that answers the next question without another walk.

## What Changed Since the 2026-08-13 Figure

The previous headline, a 3.324-second median over 901,963 entries, cannot be reproduced
and should not be compared with the number above.
Three things moved, and each is stated here rather than folded quietly into a new
figure.

**The subject is different, and deliberately so.** The 2026-08-13 tree was this
repository’s own `explorations/benchmarks/` subtree including its generated corpus,
which [the performance loop](../guides/performance-loop.md) says is not a committed
reproducible corpus and must never be compared by path or assumed count across machines.
It was cleaned up after that campaign, as the loop directs, and no longer exists.
This run uses the committed `balanced` recipe at its 1,000,000-entry scale point: seed
`fdu-balanced-v1`, 875,000 files across 125,001 directories, semantic digest
`4bbd97c0d3d4e2ad`, generated by `benchmarks.generate` and verifiable by
`benchmarks.generate verify`. Any machine can rebuild it, which the old subject could
not offer.
A generated balanced tree is also a different shape from a real checkout, with
uniform fan-out and no deep dependency thickets, so the absolute second count is not
comparable across the two subjects in either direction.

**Two of the original comparators are not in this table.** `pdu` was absent when this
matrix ran and was installed afterwards but not measured, as the limits below explain;
the Go `gdu` analyzer is still absent, so the README’s comparison against either could
not be re-measured. `/opt/homebrew/bin/gdu` on this machine is GNU coreutils’ `du`, not
the analyzer; a first run passed it under the `gdu` contract and the harness invalidated
all twelve samples with “command exited with 1”, which is the validity gate working.
It appears above under `gnu-du`, the contract that matches what it is, and `bsd-du` was
added beside it.

**fdu’s memory profile moved, because the summary tier did**, as the next section says.

## The Summary Tier Now Retains the Index

The 2026-08-13 report’s second table measured a five-tally exact summary at 3.125
seconds and 13.6 MiB, against `dumac`’s 44.4 MiB: a tier that scanned directly to five
tallies and retained no path index.
Since `.gitignore` became observed by default, an unfiltered `--view summary` must
classify entries, which the transient reducer cannot do, so the planner falls closed to
the full index. The tier still exists; `--no-gitignore` is what reaches it now.

Measured on the same tree with the same binary, three fdu contracts run against each
other round-robin, 3 warm-ups and 12 trials each:

| Invocation | Median wall | Peak RSS |
| --- | ---: | ---: |
| `fdu --cache off --depth 1 --limit 10` | 4.939 s | 285.4 MiB |
| `fdu --cache off --view summary` | 4.942 s | 285.7 MiB |
| `fdu --cache off --no-gitignore --view summary` | 4.876 s | 15.0 MiB |

Two readings matter.
The summary no longer costs less than the tree, because it now does the same work; the
0.2-second advantage the old report recorded is gone by construction, not by regression.
And the tier’s value was always memory rather than time: 15.0 MiB against 285.7 MiB on a
million entries, a 19x difference for a 1.3% time difference.
Both summaries agree exactly, at 875,000 files, 125,000 directories, 793,658,448
apparent bytes and 2,986,741,760 allocated, so the cheap tier is cheaper in memory and
no less exact.

That is `fdu-if7o` in the release’s own numbers.
The RSS figure is not a constant: it is the index’s, so it scales with retained entries
and varies with how the allocator grew its arenas on that run.
Quote a range and the mechanism, never a single multiplier.

These three medians are lower than the 5.206 seconds in the matrix above because that
run interleaves seven tools, so more of the tree’s metadata is evicted between adjacent
fdu runs. Compare rows within a table, never across them.

## Method and Validity

- **Binary.** `fdu 0.1.0-dev+g16efcd0a`, a release build of `main` at `16efcd0`, the
  0.1.0 release candidate.
  One immutable binary for every trial.
- **Pairing.** Each competitor trial runs immediately beside an fdu trial, interleaved,
  12 trials and 3 full-tree warm-ups per tool.
  The interval is a paired bootstrap on the median, `paired-bootstrap-median-95-v1`.
- **Correctness.** A Python walk independent of the engine fingerprints the tree before
  and after the run, and each tool’s answer is checked against it.
  This run recorded 0 invalid samples, 0 semantic mismatches, 0 independent
  summary-oracle mismatches, no baseline drift, and no mutation during the run.
- **Host.** Apple M1 Pro, 8 performance and 2 efficiency cores, 32 GiB, local APFS SSD,
  Darwin 25.5.0, bare metal, AC power, thermal pressure normal throughout.
- **Cache state.** Warm-steady: a repeated-workload steady state after one complete
  independent fingerprint and at least three full-tree warm-ups per tool, not a claim
  that every metadata object stayed resident.

### The Host Was Not Quiet

The predeclared regime is `uncontrolled`, and it should be read that way.
Load average ran 7.7 to 9.9 against 10 logical CPUs for the whole matrix, with other
agents building in the background; CPU busy was 33.4% at the start and 6.5% at the end.
The harness’s own quiet threshold is 0.25 load per CPU, about four times below where
this ran. Pairing is what makes the comparison survive that, since both tools in a pair
meet the same machine milliseconds apart, but the **absolute** seconds are a loaded-host
figure and a quiet machine would produce smaller ones.
Two independent matrices an hour apart agreed to within 1.5% on fdu, at 5.285 and 5.206
seconds, and within 4% on each competitor, which is the reproducibility this regime
supports and no better.

## Limits and Next Work

- Absolute seconds here belong to this subject, this host and this load.
  They are not a portable claim, and the shape of a generated balanced tree is not the
  shape of a real checkout.
- `pdu` 0.24.0 (`parallel-disk-usage`, installed with `cargo install --locked`) is now
  on this host but was not measured: two attempts at a full matrix hit host load above
  20 and free disk at the 6 GiB floor, and a number from that regime would not be
  trustworthy. The Go `gdu` analyzer is still not installed.
- The benchmark harness’s `fdu-transient-summary` contract no longer reaches the tier it
  names, for the reason given above; its argv needs `--no-gitignore` or the contract
  should be retired. Tracked as `fdu-hkyh`.
- `ncdu` was in the 2026-08-13 peer set and is not measured here.
