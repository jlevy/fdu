Making fdu faster, one measured experiment at a time

fdu is a file and directory roll-up engine. It walks a tree once and answers questions about it — folder sizes, file types, languages, prose metrics — from one reusable index, in text or JSON. It is written in Rust, with no C in its build.

On a 901,963-entry tree it builds that reusable index and renders a ten-row tree in a 3.32-second median: the fastest of every tree and index tool measured — pdu, dust, gdu, ncdu — while returning more than any of them. Its cheaper summary path ties statistically with dumac, the fastest scalar tool measured, which reports only a total. Those comparisons are recorded separately and are calibration, not evidence: a third-party tool answers a different question with different guarantees, so it never enters an accept decision.

This page is about how it got there. That work was done as an iterative research loop rather than a sequence of hunches. Every experiment — including the 28 that failed — was recorded as a validated soft-schema artifact, and this page is generated from those 64 artifacts rather than written alongside them.

It is here to show two things: how the loop works, which is a method that transfers to any system worth optimising, and what it found in this particular one — which ideas paid, which did not, and how confidently either can be said.

The loop

One experiment is one question with one answer. It names a hypothesis, builds exactly one change, and measures that change against the code it came from — both binaries interleaved in the same run, twelve paired trials, on a tree pinned by content digest. A bootstrap interval decides whether the result is distinguishable from the host having a bad afternoon, and a written rule decides whether it is worth carrying: better than 3%, with the interval clear of zero.

What makes the record usable afterwards is that the answer is stored rather than summarised. Each artifact is Markdown with validated YAML frontmatter: the frontmatter holds the measured numbers, the subject, the machine, the cost in lines and dependencies, and the verdict; the body holds the reasoning a schema cannot check. A contract validates every one of them, so the ledger and this page can be regenerated from the evidence and neither can quietly drift from it.

The soft schema is what makes the difference between a campaign and a folder of notes. Because the numbers are typed and validated, a rejected experiment costs nothing to keep — and the rejections turned out to be the most reusable part of the record.

Absolute

Wall time, in milliseconds

The campaign's own summaries are all percentages, and a percentage cannot say whether a scan takes half a second or half a minute. These are the measured medians.

Relative

What each experiment actually did

Milliseconds say how fast the tool is. They cannot say whether a particular change is why, because the host drifts: on this record the reference tool dust, whose binary never changed at all, measured anywhere from 210 ms to 327 ms on the same tree. So every experiment interleaved its two builds and compared them in pairs, and it is the paired figure below that each verdict rests on.

Most of the chart sits against the zero line. That is the ordinary shape of this work and the reason the threshold exists: an idea that seems obviously good usually turns out to be worth somewhere between nothing and two percent, and the interval is what says so before the code is carried for a year. The 28 rejections are the reusable part of the record — each one is a day the next person does not have to spend.

Scale

Does it hold on a bigger tree, and on another kernel?

Eighteen distinct trees were measured, from 307 entries to 1.01 million, on macOS and Linux. Their milliseconds are not comparable, but their cost per entry is, because a scan's work is very nearly linear in what it has to visit.

Mechanism

Two ways to make a clock go down

Work can be moved off the critical path, or it can stop happening. Both shorten wall time and only one makes the machine do less, so wall time alone cannot tell them apart. Total CPU can, and it was measured every time.

12 of these 15 deleted work outright. The rest bought their latency by spending more of the machine, which is a real gain for a person waiting on a scan and no gain at all for a laptop battery — a trade worth making knowingly rather than by accident.

The clearest pair sits at the two ends. Running the directory walk on four threads (exp‑001) cut wall time in half and raised system CPU 83%: the same syscalls, issued concurrently. Replacing those syscalls with one bulk call per directory (exp‑022) cut wall time 30% and system CPU 47%: fewer syscalls. The second kind is what let the first kind's cost be paid back later.

Reading these numbers

The two figures do not divide into each other

It is tempting to take a row from the absolute figure, divide the endpoints, and expect the relative figure's percentage. That is wrong, and the record is careful about why. The absolute values are the median of each arm on its own. The relative value is the median of the paired differences — each candidate trial against the control trial interleaved beside it. When the host drifts mid-run the two diverge, and in this record they differ by more than two percentage points on 21% of measurements and sometimes differ in sign.

exp‑005's cold-scan-index reads +2.8% if you divide its medians and −3.9% paired. The paired figure is the one that controls for drift, so it is the one the verdict used. Both are published; neither is derived from the other.

Kept and faster are different questions

The two sets nearly coincide and it would be easy to assume they are the same set. They are not, and both directions of the mismatch are worth knowing about.

5 experiments measured a real improvement and were still not kept — below the threshold, superseded, or not yet finished. 5 were kept although their interval crossed zero, because what they bought was not speed.

Instrumentation is the clearest case. exp‑052 and exp‑053 were kept on intervals of [−3.3%, +3.8%] and [−3.0%, +1.4%] — neither is a speed-up, and neither was claimed as one. What they bought was the ability to see inside the engine at a cost the measurement could not detect, which is a different thing to want and was recorded as one.

What is not measured here

Every number is one machine: an Apple M1 Pro, and one Linux VM. The page cache was warm for all of it, because dropping it needs root, so nothing here describes a genuinely cold disk. Tuning constants were fitted on the subjects shown and are inherited, not proven, on anything else.
