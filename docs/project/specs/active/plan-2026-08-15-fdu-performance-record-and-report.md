# Feature: The Performance Record, Complete and Cross-Platform

**Date:** 2026-08-15

**Author:** fdu project

**Status:** Draft

## Overview

Turn the experiment ledger into a complete, repeatable, cross-platform performance
record, ending in a generated technical report: every improvement step, accepted or
rejected, with absolute timings on macOS and Linux.

The audit behind this plan found the record stronger than feared and narrower than
wanted. All 64 committed artifacts already carry absolute wall medians for control and
candidate in nanoseconds, the subject tree’s fingerprint and entry counts, and the host,
filesystem, and cache state.
Nothing historical needs re-measuring to state what was measured.
What the record lacks is surface and span: the ledger’s tables show relative deltas
only, so the absolutes are buried in artifact bodies; and almost every experiment ran in
exactly one regime, so the cross-platform half of the story is not evidence but empty
cells.

## Goals

- Every historical experiment’s absolute timings visible in the generated ledger, not
  only its relative delta
- A per-improvement, per-platform matrix that says which cells are measured, which are
  inherited, and which are empty
- Session-scale findings promoted into artifacts, so nothing load-bearing lives only in
  beads or chat history
- A generated technical report — improvement by improvement, accepted and rejected,
  absolute walls per platform per subject — regenerated by the same target as the
  ledger, so it cannot drift from the artifacts
- Id collisions caught at commit time rather than merge time

## Non-Goals

- Rewriting or re-dating any historical artifact; the record is append-only
- Comparing absolute walls across different subject trees; absolutes are meaningful only
  within a fingerprint-matched subject, and the report must group them that way
- Claim-grade numbers from uncontrolled hosts; the evidence qualifiers exist precisely
  so exploratory runs are labelled, not laundered

## Background

Two campaigns collided on experiment ids 056–059 and were resolved by renumbering and
regeneration during the PR 29 re-stack; the ledger now validates 64 artifacts with both
campaigns coexisting.
The same review found the session-scale evidence for the snapshot-read gate
(`fdu-wpku`), the macOS validation of the consumer campaign (`fdu-m4r6`), and the peer
head-to-heads (`fdu-f6n7`) living in beads rather than artifacts, because the harness
has no job for the default one-shot CLI plan (`fdu-ao6p`). Those are exactly the
findings the technical report needs, held in the wrong container.

## Design

The report is generated, never hand-written.
`benchmarks.realtree.summary` already regenerates the ledger from validated artifacts;
the report is a second emitter over the same inputs.
Hand-authored judgement stays where it lives today — hypothesis tables and guides — and
numbers stay machine-read from artifacts.

## Implementation Plan

### Phase A: Surface what is already recorded

- [ ] Extend the ledger generator to emit an absolute-timings appendix: per experiment,
  the control and candidate wall medians, the job, the subject label with entry count,
  and the regime triple.
  No re-runs; this is presentation of existing data.
- [ ] Add the duplicate-id check to `perf-ledger` so a colliding experiment id or a bare
  hypothesis number registered twice with different titles fails the build (`fdu-f8ni`).

### Phase B: Complete the harness, promote session findings

- [ ] Land the default-CLI-plan job (`fdu-ao6p`), so the configuration users actually
  run is measurable through the harness.
- [ ] Re-run this session’s findings through it on the measured host with the evidence
  qualifiers set, and record them as artifacts: the snapshot-read gate on the 494k APFS
  subject, the H87/H88 macOS validation, and the peer head-to-heads.
  The bead notes then point at artifacts instead of carrying the numbers.

### Phase C: Fill the cross-platform matrix

- [ ] Generate the coverage matrix first: every experiment × regime, measured or empty.
  The regime-coverage table already counts; the matrix names.
- [ ] Re-run the accepted-change chain on the missing platform, in ledger order, against
  fingerprint-matched subjects, one experiment id per re-run (`validate-exp-NNN` titles,
  as exp-054 and exp-055 already model).
  Priority order: accepted changes first, then rejections whose mechanism was
  platform-specific.
- [ ] A quiet-host cell for the peer comparisons, which is what `fdu-ow8y` has been
  blocking on all along.

### Phase D: The technical report

- [ ] Emit the report: one section per improvement in chronological order, its
  hypothesis, decision, and per-platform absolute walls with intervals, grouped by
  subject; accepted and rejected both, because the rejections are the reusable half.
- [ ] Wire it into `perf-ledger` so ledger and report regenerate together.

## Testing Strategy

The generator changes are covered by the existing artifact-validation path: every number
in ledger and report is read from a validated artifact, and the duplicate-id check turns
the one observed failure mode into a build failure.
Backfill runs use the paired, interleaved protocol from
[the loop](../../guides/performance-loop.md) and the evidence qualifiers from the
Makefile; an uncontrolled host is recorded as such.

## Open Questions

- Whether rejected experiments earn cross-platform re-runs uniformly, or only where the
  refutation’s mechanism was platform-specific (H89’s glibc reasoning is the template
  for the latter).
- Whether the report should also carry the peer-tool scoreboard, which depends on
  installed third-party binaries and so validates differently than self-contained
  experiments.
