Found addressing jlevy/fdu#177 review A8. In Python, fdu.open(root).watch(WatchOptions(query=Query(views=(View.CODE,)))) builds its request with Request::read on the held basis, which refuses first with ViewNeedsAnalyzer: 'view code needs code analysis; this index was opened with analyze none'. Following that remedy (opening with analyze code) then hits the watch rule: 'analyze is not yet supported with watch; use a one-shot report'. The command line's --watch --view code refuses once, with the watch rule. Parity records the difference as class held-basis-watch (scripts/parity-classes.mjs). Consider ordering the watch's content rule before the held-basis view check on the index watch route (crates/fdu-py/src/lib.rs PyIndex::watch, crates/fdu-core/src/watch_session.rs Session::new), in the engine rather than the binding, and then retire the parity class.

## Notes

Widened by PR #177 review C1 (https://github.com/jlevy/fdu/pull/177#issuecomment-6013447138): also covers metric sorts and the CLI — `fdu --watch --view files --sort code_lines` says 'add --analyze code' (crates/fdu/src/cli.rs:1498 validates before the watch check at :842), then refuses the analyzer under --watch; the Python index watch matches. Reorder so a watch never suggests an analyzer it will refuse; align the CHANGELOG sentence.
