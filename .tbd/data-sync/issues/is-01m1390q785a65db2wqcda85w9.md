EntrySelection's terminal_extensions predicate and the MetaBrowser reference provider agree on ASCII and disagree on everything else. Found while reviewing the recovered registry/selection work now on the branch at 328ca65.

fdu, in query_selection.rs:

    fn terminal_suffix(name: &str) -> Option<&str> {
        let dot = name.rfind('.')?;
        (dot > 0 && dot + 1 < name.len()).then_some(&name[dot..])
    }

then compares with eq_ignore_ascii_case, which folds only A-Z.

The reference, catalog_terminal_suffix in contract.py at 45266a8, returns name[dot:].lower() - full Unicode lowercasing - and then compares exactly against the query values.

The boundary rule is equivalent on both sides; I checked. 'dot > 0 && dot + 1 < len' and 'not (dot <= 0 or dot + 1 == len)' accept the same names, so .gitignore and 'notes.' have no suffix and '..foo' has '.foo' in both.

Only the folding differs, and only outside ASCII. A file named archive.TÜRKÇE lowercases to .türkçe in Python and matches a query for that suffix; fdu leaves Ü unfolded, eq_ignore_ascii_case reports not-equal, and the row is dropped. Same query, same corpus, different answers - the exact class of defect the cross-provider replay under fdu-xu27 exists to catch, and the packet's non-ASCII cases will catch it.

Deciding the fix is a contract question, not an fdu implementation detail: does the contract mandate ASCII folding or Unicode folding? Record it in contract.py beside terminal_extensions either way.

- If Unicode, fdu needs full lowercasing. str::to_lowercase allocates per candidate in a filter loop, so fast-path the ASCII case and fall back only when a non-ASCII byte is present.
- If ASCII, the reference must stop calling .lower() and the contract must say query values are compared ASCII-insensitively, which will surprise anyone whose corpus is not English.

Also confirm the related claim while deciding: the contract requires query values to be lowercase, and neither provider validates that today. A query carrying '.PDF' silently matches nothing in the reference and matches everything in fdu.

Related: fdu's max_size is inclusive while the reference's size_less_than is exclusive. That one IS documented on EntrySelection ('a caller with an exclusive upper bound translates less_than: n to n - 1') and is the adapter's job, so it is correct as written - noted here so a reviewer does not re-flag it.
