Found while assessing the second half of fdu-0778 (skip re-reading unchanged control files), at `afe0f89` on codex/opened-root-inventory-rewrite (PR #48).

**Defect.** Reconciling a subtree whose root is a retained `.gitignore` file updates the file's entry and never reads its content. The control table keeps the old source, and the pass reports complete and marks the path `Fresh`.

`reconcile_target_inner` (`crates/fdu-core/src/scan.rs:3546-3554@afe0f89`) handles a non-empty subtree root: a `ControlOnly` root reads its control (`scan.rs:3534-3541`), but a `Retain` root only pushes the upsert, flushes, and returns because a file does not descend. The listing walk reads the control after every retained entry (`scan.rs:3622-3631`); the subtree-root branch has no such read.

**Reproduced** (scratch test, not committed): a tree with `.gitignore` = `*.log` and `a.log`; `scan_into_index`; rewrite `.gitignore` to a comment; apply `InvalidateSubtree { path: ".gitignore", reason: Requested }`; `reconcile_pending`. Result: `report.is_complete() == true`, `freshness_at(".gitignore") == Fresh`, `is_ignored("a.log") == Some(true)`, and the table still holds `*.log`.

**Who reaches it.** Any file-rooted reconciliation of a retained `.gitignore`: a library `InvalidateSubtree` on the file, an opened root's `refresh` of that path (`reconcile_paths_target` calls the same inner function), or a watch rescan hint that names the file. Hidden-pruning scopes are not affected, since there the file is `ControlOnly`.

**Fix direction.** In the `Retain` branch of the subtree root, read the control after the upsert exactly as the listing walk does, conditioned on the same baseline, and push any read error into `report.scan.errors`. Test: the reproduction above, asserting the rule is gone and the path is not claimed fresh on a read error.

**Why it matters for fdu-0778.** It is one of the ways an entry's attrs can move while the control table stays behind, which is why "attrs unchanged" cannot justify skipping the read today.
