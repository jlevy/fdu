## Notes

entry_page is resumable because path order is a total order the tree already
holds: a cursor is the last path emitted, and "the first match strictly greater"
is a descent. Any other order loses that.

"Recently changed" is the case a browser actually asks for, and the example's
recent_slice is still a slice rather than a page because of it: Selection.limit
bounds the rows and the section says how many it withheld, but there is no
cursor to resume from and no exact remainder conserved to a terminal page. A
consumer cannot assemble a complete recency answer from bounded requests.

Two shapes could work, and they cost differently:

- A cursor carrying the sort key beside the path, so a resume is "strictly after
  (mtime, path)". No maintained index needed, but every page still scans the
  selection to find its own window -- which is the cost fdu-91ru just removed for
  path order, so this would reintroduce it for sorted queries.
- A maintained index over the sort key, which makes the seek a range query and
  costs a reducer-path update per mutation. That is the same trade planes made,
  and the measurement (fdu-n4gn) is the precedent for deciding it.

Do not start this without a reason a consumer states: an unsorted catalog page
plus a bounded recency *slice* may be enough, and a maintained mtime index is a
cost every write pays for a projection some consumers never read.

Blocked on nothing technically. Named here so the example's honest note has
somewhere to point.
