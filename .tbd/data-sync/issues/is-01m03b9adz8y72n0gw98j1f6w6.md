Requirement from product use: a UI wants instant approximate values from the snapshot when one exists, converging as verification completes, and a normal scan when it does not.

Neither existing policy serves this. CachePolicy::Only answers without touching the tree but hard-errors when no usable snapshot exists ('no usable snapshot for this root and scan scope'), which is a deliberate design decision so the fast path stays predictable and does not silently become a scan. CachePolicy::Auto reads and revalidates, but revalidation stats every entry, so it costs a full walk and gives no instant paint.

Measured value of the snapshot-only read (Linux/ext4, /usr, 84,539 entries, cold OS cache): 118 ms against 277 ms for a cold scan, -57%. Warm, it loses: 81 ms against 71 ms. So the tier is worth having exactly where the walk is expensive, which is the case the UI cares about.

Proposal: a tier that prefers the snapshot when one is usable and falls back to a live scan when it is not, with the distinction visible in provenance rather than hidden. This must not weaken Only's strict contract; it is an additional tier, not a change to that one.

Depends on the provenance work already tracked under this epic (fdu-fka6, fdu-0k92, fdu-lq0v, fdu-1mj4): an approximate answer is only acceptable if every value carries its own confidence and the CLI and Python surfaces show it. Do not ship the fallback before values can be labelled.

Acceptance: the tier is reachable from CLI and the Python API; a snapshot-served answer is marked unverified and never claims currency it has not earned; absence of a snapshot degrades to a scan without error; and the strict Only contract is unchanged and still tested.
